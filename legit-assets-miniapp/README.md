# Legit Assets v16 — клієнт, адмінка та Railway

**Один сервіс Mini App. Окремий Postgres, DATABASE_URL і зовнішні сервіси БД не потрібні.**

При запуску застосунок сам створює `legit.sqlite` на приєднаному диску, застосовує схему, додає початковий каталог і запускає обробник замовлень. Тимчасові дані очищуються за правилами 72 годин. Це реальна SQLite, не демонстраційна база в пам'яті.

## Формат із 20 файлів

Основні ui.tsx, server.tsx, shared.tsx, views.tsx, CSS і каталог залишені окремими. Маршрути Next.js, proxy, Prisma-схема та міграція, тести, tools.ts і допоміжні файли об’єднані в **project.pack.json**. Текст коду відкритий у JSON, не мінімізований; PNG збережено в base64 без втрат. Це приватний пакет вихідного коду, окремий від публічних зображень assets.pack.json.

`npm ci` автоматично відновлює службові файли й генерує Prisma Client. Docker робить те саме до збірки. Команди build/test/start також перевіряють їх наявність. Нічого вручну розкладати по папках не потрібно. **20 — кількість файлів у ZIP/репозиторії; після встановлення та збірки створюються додаткові робочі файли Next.js, Prisma й node_modules.**

Для редагування службового коду виконайте `npm run source:extract`, відредагуйте потрібний відновлений файл і виконайте `npm run source:pack`. Зміни запишуться назад у єдиний project.pack.json. Якщо файл відредагований, повторна підготовка не перезапише його мовчки, а попросить спочатку зберегти зміни командою source:pack. Не додавайте в пакет секрети чи файли БД.

При переході зі старої версії замініть вихідну папку цілим новим комплектом, зберігши приватний .env і Railway Volume. Не накладайте її поверх старих маршрутів/міграцій. У Git відстежуйте лише 20 файлів комплекту; список відновлюваних файлів додано до .gitignore.

## Деплой: що зробити один раз

1. Розпакуйте ZIP. Вміст папки `legit-assets-miniapp` покладіть у корінь репозиторію: там мають лежати Dockerfile та package.json. Якщо папка лишилася вкладеною, Root Directory у Railway має бути `/legit-assets-miniapp`.
2. Створіть сервіс Railway із цього репозиторію. Додайте до **цього сервісу** один Volume з Mount Path `/data`. Це диск для файлу бази, не окремий сервіс БД. Railway передає шлях через RAILWAY_VOLUME_MOUNT_PATH; вручну його вводити не треба.
3. У Variables приберіть старі DATABASE_URL і DIRECT_URL, якщо вони залишилися. Збережіть BOT_TOKEN, ADMIN_ID, ключі постачальників та постійні приватні ключі існуючого магазину.
4. Для першого запуску згенеруйте секрети командою `node scripts/start.mjs env --railway` (працює без npm install). У створеному railway-variables.env заповніть BOT_TOKEN і власний числовий ADMIN_ID, скопіюйте вміст у Variables → Raw Editor. Сам файл не завантажуйте в GitHub. Для існуючого магазину не генеруйте новий DELIVERY_ENCRYPTION_KEY.
5. Networking → Generate Domain. Залиште одну репліку сервісу. Ручні Build/Start Commands не потрібні: використовується Dockerfile. Файл railway.json уже задає Dockerfile, healthcheck `/api/health` (180 секунд) і повторний запуск при аварії.
6. У BotFather задайте HTTPS-адресу Mini App для @LegitAssetsBot. Python-бот залишається окремим застосунком; його банківські webhooks цей ZIP не реєструє.

Після цього база підключається автоматично. При повторному деплої використовується той самий файл на Volume. Без Volume запуск у Railway зупиниться з поясненням, щоб магазин не створив базу на ефемерному диску й не втратив її після перезапуску.

Документація Railway Volume: https://docs.railway.com/volumes . Документація SQLite/Prisma: https://docs.prisma.io/docs/orm/v6/overview/databases/sqlite . Сам Volume цей архів не створює через API Railway — його потрібно додати в панелі один раз.

## Перші дії адміністратора та клієнта

Адміністратор: відкрийте Mini App саме з акаунта, числовий ID якого є в ADMIN_ID. Завершіть вибір мови та вступну екскурсію. У профілі відкрийте адміністративний вхід; він перевіряє підпис Telegram, пароль вигадувати не потрібно. Нік @username не замінює числовий ADMIN_ID.

В адмінці є керування товарами й складом, замовленнями, ручною видачею, поверненнями, SMM-чергою та журналом змін. Перевірте ціни й наявність перед відкриттям продажів. Розділ «Операції» показує готовність інтеграцій, worker і розмір SQLite. Додано пояснення для NFT API та з'єднання з балансом бота; жодні ключі в цьому звіті не показуються.

Клієнт: перший вхід → мова → одноразова екскурсія → Магазин / NFT / Історія / Профіль. У профілі можна змінити фото. Поповнення гривневого балансу веде до бота; Monobank не переноситься в цей вебзастосунок. NFT оплачуються GRAM через підключений гаманець.

Без ключів постачальників не можна обіцяти живі NFT або автоматичне виконання SMM. Фолбек NFT не продається як справжній актив. Для бойового запуску підключіть BOT_BRIDGE_URL/секрети до існуючого бота, API постачальників і виконайте контрольне замовлення кожного ввімкненого типу. Реальні гроші під час локальних перевірок не використовувалися.

## Резервна копія без зупинки магазину

```bash
npm run db:backup -- /data/backup-2026-10-15.sqlite
```

Команда використовує SQLite backup API і враховує підтверджені дані у WAL. Вона не перезаписує існуючий файл, не створює копії в public/ та встановлює приватні права 0600. Батьківська папка повинна існувати. Після створення заберіть копію з Volume у приватне сховище; постійні копії на диску 1 ГБ накопичувати не треба. Копії містять персональні й фінансові дані.

Для відновлення: зупиніть сервіс, збережіть поточну базу разом із WAL/SHM окремо, замініть legit.sqlite перевіреною копією та приберіть старі файли legit.sqlite-wal/legit.sqlite-shm з робочої папки перед запуском. Збережіть незмінним DELIVERY_ENCRYPTION_KEY: без нього зашифрований склад із копії не відкриється. Відновлення робіть лише після звірки нових платежів, щоб не відкотити вже виконані покупки.

## Оновлення попередньої версії

**Замініть папку prisma/migrations повністю.** У цій версії одна початкова SQLite-міграція. Не залишайте поруч старі PostgreSQL SQL-файли: вони несумісні. Старт перевіряє наявність старих міграцій і пояснює, що треба замінити папку.

Якщо ви вже реально використовували попередню PostgreSQL і там є замовлення, автоматичного перенесення їх у SQLite немає. Не видаляйте стару базу: спершу потрібне окреме перенесення даних і звірка балансів. Ця версія автоматично ініціалізує новий SQLite-файл; при наступних запусках зберігає його. Ботівська SQLite-база також не переноситься і не підміняється.

З попередніх версій не повинні залишатися `src/api.ts`, `src/app/admin/page.tsx`, `src/app/admin/login/page.tsx`, `src/app/admin/operations/page.tsx`. Замість них — чинні server.tsx і один адмінський dispatcher. ZIP містить повний знімок проєкту.

## Тимчасові дані: 3 дні

- Кошик та обране — 72 години після останньої зміни. Вони зберігаються на пристрої/у Telegram, а не роздувають SQLite. При відкритті прострочене значення не відновлюється; на закритому пристрої фізичне очищення відбудеться при наступному відкритті.
- Фото та відображуване ім'я неактивного клієнта очищуються через 72 години без авторизованої активності.
- Порожній Telegram-профіль видаляється після 72 годин неактивності, лише якщо немає покупок, оплат, ненульового балансу, транзакцій, NFT, активних сесій чи іншої незавершеної роботи. При поверненні такий користувач створюється заново, вибір мови/екскурсія повторяться.
- Сесії, handoff та wallet-proof токени видаляються після свого коротшого строку дії.
- Текст уже доставленого службового повідомлення очищується через 3 дні; його ключ захисту від повторного надсилання зберігається.
- Баланси, платежі, історія замовлень, NFT-підтвердження, товари, склад та адміни не стираються за таймером.

Worker запускає очищення щогодини, до 200 рядків на таблицю за раз. Великий backlog очищується кількома порціями. Активні користувачі не видаляються кожні 3 дні. Ботівський Monobank-облік не зачіпається.

## Місткість і точність

Аватар перетворюється на WebP до 64 КіБ; оригінал до 2 МБ не зберігається. Зображення каталогу лишаються ресурсами застосунку. Перевірка сесії не читає байти аватара при кожному запиті.

Синтетична SQLite-база з 300 активними користувачами, аватарами по 64 КіБ та тестовими замовленнями зайняла приблизно **19,33 МіБ**. WAL та резервні копії займають додаткове місце. Це перевірка місткості, не гарантія 300 одночасних покупок або безмежного зростання історії в 1 ГБ.

Грошові колонки — TEXT з точними десятковими значеннями. Арифметика виконується через decimal.js з точністю 40 значущих цифр; фінансові суми не складаються через SQLite REAL або JavaScript Number. Підсумки адмінки також рахуються точно. Зміни балансу й замовлень відбуваються в транзакціях, з перевіркою версії гаманця та збереженими ідемпотентними ключами.

SQLite працює в WAL-режимі; записи серіалізуються. Використовуйте одну репліку з одним Volume. Для великого числа одночасних записів потрібен окремий навантажувальний тест. Не копіюйте лише основний SQLite-файл під час активних записів без врахування WAL: для бекапу використовуйте узгоджений snapshot зупиненого сервісу або SQLite backup API.

Адмінка → Операції → Готовність до запуску показує розмір БД, кількість користувачів і останнє очищення. Від 700 МіБ пропонує перевірити місце. Повний обсяг дивіться у Railway Volume Metrics; звіт бази не включає всі супутні файли. Видалені сторінки повторно використовуються — файл не зобов'язаний одразу зменшитися.

## Команди

```bash
npm ci
npm run db:generate
npm run env:init -- --domain=your-real-domain.com
# Заповніть свої Variables/.env.
npm run build
npm start
```

Локально без DATA_DIR база створюється в `.data/legit.sqlite`. Цей каталог, WAL/SHM і приватні .env виключені з Git та Docker-контексту.

```bash
npm run db:check      # перевірка підключення, міграції й таблиць
npm run test:launch   # після build: клієнт/адмін і повторний запуск на тимчасовій БД
npm run db:storage    # розмір SQLite та місце для повторного використання
npm run db:cleanup    # одна порція безпечного очищення
npm run launch:check  # готовність ключів/worker/інтеграцій
npm run verify       # тести, TypeScript, production build, аудит клієнтських ресурсів
```

`npm run db:deploy` застосовує міграції вручну, якщо це потрібно. При звичайному Railway-старті це автоматично. `npm run deploy:files` генерує VPS Compose і Nginx-шаблони без перезапису існуючих; `npm run db:local` запускає єдиний контейнер з SQLite volume, без Postgres.

## API та бот

- LZT_TOKEN: raw access token зі scope market, без Bearer. Сервер сам додає Bearer. https://lolz.live/account/api/client-add та https://lolz.live/account/api/get-token .
- MARKETAPP_API_TOKEN: живий NFT-каталог/купівля; без нього показується позначений SVG-фолбек. TONCENTER_API_KEY рекомендовано для перевірок blockchain.
- SMM_API_KEY та схвалений service map потрібні для SMM. Реальні замовлення вмикаються окремим SMM_LIVE_ORDERS_ENABLED=true після перевірки постачальника. LZT покупки аналогічно через MARKET_LIVE_ORDERS_ENABLED.
- BOT_BRIDGE_URL у Mini App веде до вашого Python-бота; MINIAPP_API_URL у боті — до Mini App. BOT_WEBHOOK_SECRET і BOT_BRIDGE_SECRET мають збігатися на обох сторонах. Банківський токен і webhook налаштовуються у боті.
- NFT купується нативним GRAM-гаманцем через TON Connect. Підтверджується фактичне отримання NFT; комісія магазину — окремий другий переказ після отримання. Ці два перекази не атомарні. Внутрішній баланс бота автоматично не списується для NFT.
- Наявність API-ключа не гарантує право доступу до постачальника або наявність товару. Живі покупки потрібно перевірити власними контрольними замовленнями.

## Перевірено у v16

- 106/106 тестові вузли; збережені перевірки безпеки/торгівлі, deploy-тести адаптовані до автоматичної SQLite.
- TypeScript без помилок та production build. Виправлено втрату точності великих сум у відображенні історії й адмінських звітів.
- Перевірено узгоджений online-backup SQLite з WAL, приватні права копії та відмову перезаписувати файл.
- У попередній v14 перевірено 16 інтеграційних сценаріїв на справжньому локальному SQLite: повторні оплати, баланс, повернення, Stars, SMM/LZT, склад, handoff, retention та точність дробів понад Number.MAX_SAFE_INTEGER. Зовнішні платіжні запити замокані.
- `npm run test:launch`: production-сервер із тестовими Telegram-підписами перевіряє вхід клієнта, вимогу вибору мови перед екскурсією, завершення екскурсії, вихід, заборону поповнення напряму, відмову звичайному користувачу в адмінському вході та доступ адміністратора до огляду, замовлень, товарів і сховища. Зовнішні постачальники не викликаються.
- Реальний запуск без DATABASE_URL: файл створився, міграція і seed пройшли, вебсервер та worker запустилися. Перевірені основні HTTP-маршрути й закритий доступ до адмінських даних.
- Повторний запуск із тим самим каталогом зберіг тестового користувача та не продублював 13 початкових товарів. WAL увімкнений.

Railway-акаунт і Docker Volume у вашому середовищі не тестувалися. Гілка зміни власника volume та скидання root-привілеїв призначена для Docker; локальний smoke-тест запускався без цієї контейнерної гілки. Реальні NFT/Monobank-платежі не виконувалися. Повний браузерний регресійний прогін попередньої версії не повторювався: у цій версії перевірено HTTP-запуск, типи та реальні DB-сценарії.

## Структура

Основна логіка лишилася у src/ui.tsx, src/shared.tsx, src/server.tsx і src/views.tsx. Усі 193 ресурси збережені в assets.pack.json. Для редагування картинок: `npm run assets:extract`, потім `npm run assets:pack`. Історичні SQL та deploy-шаблони збережені в `legacyPostgresArchive` у scripts/start.mjs виключно як довідковий код; клієнт їх не завантажує, запуск їх не виконує. Чинна папка міграцій містить лише SQLite-схему.

Архів містить **рівно 20 файлів**. Усі 29 об’єднаних файлів збережені побайтово в project.pack.json із SHA-256. Їхній код, тести, схема БД й ілюстрація не видалені. Логіку й каталог не видалено: 11 історичних SQL-міграцій збережені в серверному архіві коду, активна схема замінена на одну SQLite-міграцію.
