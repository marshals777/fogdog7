# Legit Assets — компактна Telegram Mini App

Основний код об'єднано у п'ять файлів:

- `src/ui.tsx`: інтерфейс, компоненти, профіль, екскурсія, каталог, адмінка та клієнтські хуки.
- `src/shared.tsx`: переклади, навігація, точні розрахунки та спільні типи.
- `src/server.tsx`: авторизація, бізнес-логіка, постачальники, оплати, бот і NFT.
- `src/api.ts`: усі HTTP-обробники. `src/app/api/[...path]/route.ts` зберігає старі адреси API.
- `src/views.tsx`: серверні представлення каталогу й інформаційних сторінок.

`assets.pack.json` містить усі 193 початкові зображення й анімації без зміни байтів. Їхні URL збережено. Невеликі файли `page.tsx`, layout та модальні маршрути залишено для сумісності Next.js. Код не заховано у ZIP-рядках і не відновлюється в сотні файлів перед запуском: це справжня консолідація TypeScript. Коментарі та namespaces позначають попередні модулі.

## Запуск

Потрібні Node.js 22.18+ та PostgreSQL. Збережіть стару базу й резервну копію перед міграціями.

```bash
npm ci
cp .env.example .env
# Заповніть .env власними параметрами.
npm run db:generate
npm run db:deploy
npm test
npm run typecheck
npm run build
npm start
```

У `.env` задайте `DATABASE_URL`, `NEXT_PUBLIC_SITE_URL` (ваша публічна HTTPS-адреса), `BOT_TOKEN`, `NEXT_PUBLIC_BOT_USERNAME` та решту параметрів сервісів. Наявні дані PostgreSQL не переносіть у нову порожню базу: застосовуйте міграції до наявної. Нова міграція `20261013045000_nft_checkout` додає таблиці доказу гаманця та NFT-замовлень, не змінюючи балансів.

## Реальна купівля NFT за GRAM

Підключено офіційні `GET /v1/nfts/{address}/` і `POST /v1/nfts/buy/` Marketapp. Потрібен ваш серверний `MARKETAPP_API_TOKEN` із доступом до платного NFT API. Для стабільної перевірки блокчейну задайте `TONCENTER_API_KEY`. Токени не передаються браузеру. У документації Marketapp: https://api.marketapp.org/docs/.

1. Пройти перший вибір мови та екскурсію.
2. Обрати **живий** NFT. SVG-фолбек позначено демонстраційним і купівля з нього не запускається.
3. Натиснути «Підтвердити гаманець» та погодити `ton_proof`. Потрібен основний блокчейн; ця версія перевіряє ключ уже активованого гаманця через `get_public_key`. Для свіжого неактивованого гаманця спершу активуйте його у застосунку гаманця.
4. Натиснути «Підтвердити купівлю». Сервер повторно перевіряє поточну ціну, валюту GRAM/TON (назви нативної монети), строк транзакції та поточного власника. USDT для NFT відхиляється. Гаманець показує й підписує реальну транзакцію купівлі.
5. Сервер перевіряє власника **та успішну транзакцію transfer** потрібного NFT від попереднього власника до підтвердженого покупця. Хеш транзакції видачі унікальний: одна передача не створює повторних оплат.
6. Після видачі — окреме підтвердження збору 7% на магазин `UQBhos7uoI_1Fs4HCUWUEqv3ZVwKb_EWuHeOO7LMH2t34Wwl`. Повна ціна товару дорівнює базі + 7%; мережеві витрати окремо показує гаманець. Збір не стягується до видачі. Гаманець запитає два підписи, а не один.
7. «Оплату завершено» з'являється лише після підтвердження у блокчейні надходження збору: перевіряються адреси, сума, час, коментар замовлення та унікальний хеш. Повторний запуск збору захищено п'ятихвилинною серверною блокіровкою. Якщо підпис відхилено, дочекайтеся завершення цього строку перед новою спробою.

Продовжити незавершене NFT-замовлення можна з **Історії**. Непідписаний/прострочений запит не позначається оплаченим. Після прострочення перевірте отримання перед створенням нового запиту. Демонстраційна кнопка, BOC-відповідь гаманця або клієнтський POST самі по собі не підтверджують видачу/оплату. Приватні ключі/seed гаманця магазину не потрібні: покупець підписує покупку сам.

Важлива межа: прямий NFT-checkout видає NFT у гаманець покупця; він не списує GRAM зі старого внутрішнього балансу Python-бота. 7% — окремий платіж після видачі. Якщо покупець не завершує збір, NFT уже належить йому, а замовлення має статус «збір очікує оплати». Код не обіцяє атомарного стягнення двох платежів або автоматичного показу on-chain NFT у Telegram-профілі.

## Профіль і поповнення через бота та Monobank

Збережено чотири вкладки: Магазин, NFT, Історія, Профіль. Вибір мови й одноразова екскурсія зберігаються в PostgreSQL. Завантаження/видалення фото: PNG/JPEG/WebP до 2 МБ, серверні 256×256 WebP без метаданих. Усі попередні категорії, SMM, адмінка, CloudStorage, Safe Areas, Telegram-тема та ефекти натискання збережено.

Поповнення відкриває Python-бота `miniapp_topup_uk/ru/en`. Баланс UAH/GRAM береться з його наявної SQLite-бази. Mini App не створює другий зарахувач коштів. Використовуйте вже наданий `legit-bot-integrated.zip` та його `MINIAPP-INTEGRATION-UA.md` для Monobank. Не запускайте старий Monobank relay одночасно з новим обробником.

На обох серверах — однакові окремі `BOT_WEBHOOK_SECRET` та `BOT_BRIDGE_SECRET` від 32 символів. `BOT_UPDATE_OWNER=standalone`, `BOT_WEBHOOK_ENABLED=true`; `BOT_BRIDGE_URL=https://BOT-DOMAIN` проксує читання `/balance`. Telegram-оновлення приймає Python-бот, передаючи тільки події Mini App до `/api/bot/webhook`. API-адреси після консолідації збережено.

## Перевірки та межі

55 попередніх тестів + 6 NFT-тестів + 1 тест пакета зображень: **62/62**, усі початкові 30 тестів збережено. TypeScript strict і production-збірка проходять. Профіль, фото, онбординг, вкладки й категорії перевірено у браузері на ширинах 320/390/430. Окремий браузерний сценарій через справжній TON Connect SDK із синтетичним injected-гаманцем пройшов: ton_proof → підпис купівлі → видача → блокіровка збору → підпис збору → завершення. Приватні маркери чотирьох серверних параметрів перевірено на відсутність у клієнтській збірці. JSON-пакет має лише дозволені публічні ресурси, без вихідного коду, БД чи секретів.

Тести використовують синтетичний гаманець, відповіді API та підтвердження блокчейну. Справжні платежі не виконувалися, робоча БД не запускалася й ваші реальні токени не налаштовувалися. Це готовий код шляху покупки, а не доказ проведеної живої угоди. Після налаштування потрібен контрольний сценарій на вашому сервері з вашим гаманцем. Комерційні ключі й доступ до платного API потрібно надати власнику магазину.

## Що потребує налаштування перед продажами

Домен/HTTPS, PostgreSQL, нові приватні API-ключі, робочий бот, платіжні кабінети/webhook-и, курс валют та тариф Stars. Реальні секрети в архів не включені. Опубліковані раніше в чаті токени слід замінити. Автоматичні закупівлі за замовчуванням вимкнені; при цьому checkout постачальника також заблокований і баланс не списується.

Це код інтеграцій і перевірений локальний проєкт, а не підтвердження бойового деплою чи приймання платежів. Платіжні й закупівельні сценарії перевірені на fixtures; перед увімкненням продажів потрібні sandbox платежі та контрольне замовлення кожного постачальника. Формат закритих даних LZT після реальної покупки треба звірити: невідомий формат навмисно зупиняє видачу для перевірки.

Не реалізовані: форми специфічних SMM типів Custom Comments/Subscriptions/Package тощо (вони позначені як недоступні для checkout), Fondy (обрані Mono/Stripe), автоматична обробка chargeback депозитів, email verification/password recovery та об’єднання email і Telegram облікових записів. Верифікації виконуються власником магазину вручну. Повернення WEB-замовлення зараховується на внутрішній баланс, а не автоматично на банківську картку.

## Захист і межі готовності

API-ключі, PostgreSQL та бізнес-логіка залишаються на сервері; клієнту доступний лише публічний інтерфейс і дозволені дані. CSP з nonce, блокування службових шляхів, відсутність публічних source maps, CSRF, серверна перевірка ролей і власника покупки працюють разом. WEB/TMA мають окремі HttpOnly сесії; TMA cookie у production — Secure, SameSite=None, Partitioned. Адмін-панель забороняє вбудовування в iframe. `npm run security:audit` перевіряє зібрані JS-файли на значення секретів, наданих його середовищу; без них він не може перевірити невідомі ключі.

Захистити публічний вигляд від копіювання повністю неможливо: браузер завжди отримує HTML/CSS/JS. Katana та інші crawlers можуть бачити публічні маршрути; це не повинно давати їм доступ до БД, адмінки чи серверних файлів. Блокування правої кнопки/DevTools цього не вирішує. Приклади nginx і приватної Docker-мережі в `deploy/` потрібно застосувати й перевірити на вашому сервері; зараз інфраструктура не розгорнута.

Для Google потрібні реальний HTTPS-домен, SEO_ENABLED=true після перевірок, актуальні sitemap/robots і Search Console. Код сам не підтверджує індексацію чи позиції. Повний звіт і невиконані production-перевірки: SECURITY_AUDIT_V8.md.

# Legit Assets v9 — запуск одного магазину

Архів сайта містить WEB, Mini App і спільний API. Архів бота — окремий Node-процес. Не потрібно деплоїти старі магазини окремо. Основні розділи: Steam, Telegram за країною/спамблоком, SMM JustAnotherPanel, верифікації, Telegram NFT Подарунки (MarketApp API з преміальними візуальними ефектами). Додаткові модулі — `/uk/modules`, `/ru/modules`, `/en/modules`; кожен має незалежну адресу й Telegram-посилання.

## 1. Підготувати сервер і домен

Для цього набору рекомендована схема VPS + PostgreSQL 16 + nginx HTTPS; бот можна розмістити на іншому сервері. Docker Compose приклад уже включає окремий commerce worker. У поточному середовищі Docker/nginx не запускалися — перевірити на цільовому сервері.

Розпакуйте сайт у приватний каталог поза статичним web root. Node >=22.18 потрібен для локального npm; у Docker він уже є. Створіть секрети на сервері:

```bash
npm run env:init -- --domain=your-real-domain.com
```

Команда генерує випадкові ключі шифрування/bridge/cron і узгоджений пароль PostgreSQL, записує `.env` із правами 0600 і **ніколи не перезаписує існуючий файл**. Для оновлення v8 збережіть поточний DELIVERY_ENCRYPTION_KEY і БД: новий ключ зробить стару видачу нечитабельною.

## 2. Додати свої нові ключі в .env на сервері

Потрібні BOT_TOKEN, username бота, нові LZT_TOKEN і SMM_API_KEY, хоча б один WEB-платіжний провайдер, STARS_USDT_PER_STAR та bootstrap email/password адміністратора. Старі токени з чату замініть. У чат або Git ці значення не вставляйте.

Crypto Pay для справжніх коштів: CRYPTO_PAY_TESTNET=false. Stripe потребує STRIPE_SECRET_KEY і STRIPE_WEBHOOK_SECRET. Mono — MONO_TOKEN. Курси валют: FX_MODE=lzt з робочим LZT_TOKEN; manual режим вимагає всіх курсів і регулярного оновлення timestamp.

## 3. Запустити сайт і міграції

```bash
docker compose --env-file .env -f deploy/compose.site.yml build
docker compose --env-file .env -f deploy/compose.site.yml up -d db
docker compose --env-file .env -f deploy/compose.site.yml run --rm site npm run db:deploy
docker compose --env-file .env -f deploy/compose.site.yml run --rm site npm run admin:seed
docker compose --env-file .env -f deploy/compose.site.yml run --rm site npm run admin:create
```

Після створення адміна видаліть ADMIN_BOOTSTRAP_PASSWORD із .env. Замініть домен і шляхи TLS-сертифікатів у `deploy/nginx.conf.example`, перевірте `nginx -t` і налаштуйте DNS/HTTPS. БД не має опублікованого порту; сайт доступний nginx на 127.0.0.1:3000.

```bash
docker compose --env-file .env -f deploy/compose.site.yml up -d site worker
docker compose --env-file .env -f deploy/compose.site.yml exec site npm run preflight
```

Публічний `/api/health` перевіряє доступність БД і повертає тільки `{ok:true|false}`. Це не перевірка платежів. Детальний стан доступний тільки адміністратору: `/admin/operations` → «Готовність до запуску». Він показує налаштування, актуальний FX, каталог і останній успішний tick worker; секрети у відповіді відсутні. Свіжість heartbeat — 3 хвилини.

Якщо ви деплоїте сайт на Vercel, worker запускається окремим довготривалим Node/Docker-процесом з HTTPS origin і INTERNAL_API_SECRET; не через браузер або короткий cron. PostgreSQL має бути зовнішнім із pooler. API закупівель може працювати до 120 секунд — план/таймаути хостингу потрібно перевірити. Цей варіант не тестувався на вашому Vercel-проєкті.

## 4. Окремо запустити бота

У `.env` бота задайте BOT_TOKEN, SITE_URL вашого домену, той самий INTERNAL_API_SECRET. BOT_STATE_DIR — постійний диск для журналу оплат Stars. COMMERCE_WORKER_ENABLED=false, коли працює standalone worker; якщо окремого worker немає, true. Незалежно від цього бот обробляє Stars-журнал і сповіщення.

```bash
npm ci
npm run build
npm start
```

Процес бота має перезапускатися supervisor-ом. Для одного токена лише один polling-процес. BotFather: Web App/menu button, домен Telegram Widget, за бажанням Mini App short name; NEXT_PUBLIC_MINI_APP_NAME у сайті має відповідати short name. Публічні NEXT_PUBLIC_* задаються перед build, їх зміна потребує перебудови.

## 5. Приймання перед відкриттям продажів

На цільовому сервері перевірте: WEB вхід і баланс; оплату/повторний webhook; Telegram Stars; ручну видачу; одноразовий склад; контрольну SMM Default послугу й polling; контрольну закупівлю LZT та формат видачі. Не вмикайте live flags до перевірки; увімкнення прапора саме по собі не перевіряє ключі/контракти/баланс постачальника.

Після приймання виставте MARKET_LIVE_ORDERS_ENABLED=true, SMM_LIVE_ORDERS_ENABLED=true, SEO_ENABLED=true й перебудуйте/перезапустіть відповідні процеси. У runtime .env і build args SEO повинні збігатися. Google Search Console потребує доступу до вашого домену.

```bash
docker compose --env-file .env -f deploy/compose.site.yml exec site npm run launch:check
```

Strict check також потребує увімкнених supplier/SEO flags і видаленого bootstrap-пароля. Навіть його зелений результат підтверджує конфігурацію, а не фактичну оплату або безумовну доступність зовнішніх API.

## Межі цього релізу

SMM автоматизовано для Default; інші форми заблоковані. Верифікації видає адміністратор. Email/Telegram акаунти окремі; автоматичного linking, email reset/MFA й повного циклу chargeback/часткових SMM refunds немає. Це не перешкоджає основним описаним сценаріям, але оператор має обробляти NEEDS_REVIEW і фінансові винятки.

У QA пройшли fixtures і HTTPS Chromium, включно з кошиком WEB→TMA, owner-check, CSRF, iframe та readiness UI. Нативний PostgreSQL не вдалося запустити в доступному середовищі: немає придатного non-root UID для postgres. Нативні міграції, конкуренцію, backup/restore та Docker потрібно перевірити на цільовому сервері. Реальних оплат, закупівель і Telegram-повідомлень тут не здійснювали.

# Деплой v7: сайт і бот окремо

## 1. База й секрети

Створіть PostgreSQL (рекомендовано керований з backup/PITR), DATABASE_URL без публічного доступу до БД. Сайт має доступ до БД; бот — лише HTTPS API сайту. Резервуйте БД та DELIVERY_ENCRYPTION_KEY окремо: без цього ключа видані файли не відновити. Заміна ключа без міграції старих шифротекстів робить їх непридатними.

Згенеруйте DELIVERY_ENCRYPTION_KEY (32 байти base64), INTERNAL_API_SECRET і CRON_SECRET (не менше 32 випадкових символів). У браузер дозволені лише NEXT_PUBLIC_SITE_URL, NEXT_PUBLIC_BOT_USERNAME, NEXT_PUBLIC_TELEGRAM_MOCK=false. BOT_TOKEN, JAP/LZT/платіжні ключі — тільки секрети серверів. Не вставляйте їх у Git, скриншоти або клієнтський код.

## 2. Сайт

Потрібні Node >=22.18, вихідний HTTPS до Telegram, LZT, JAP та вибраних платіжних API. Для production задайте NEXT_PUBLIC_SITE_URL=https://ваш-домен без підшляху. Один канонічний origin: інші домени перенаправляйте на нього. Reverse proxy має передавати оригінальний Host/Origin; mutations захищені перевіркою Origin.

```bash
npm ci
npm run db:generate
npm run db:deploy
npm run admin:seed
npm run admin:create
npm run build
npm start
```

Next читає `.env`; CLI Prisma також читає `.env`. Для hosted environment задавайте серверні змінні через панель секретів. NEXT_PUBLIC_* потрібні під час build. `npm run db:migrate` тільки для розробки; бойовий деплой — `db:deploy`.

Є Dockerfile. Задайте build args NEXT_PUBLIC_SITE_URL/NEXT_PUBLIC_BOT_USERNAME. Образ запускає Node як `node`, env надходить від хостингу. Міграції та seed виконайте одноразовим deployment job до запуску нового релізу. HTTPS завершується на reverse proxy; зовнішній HTTP production не підтримується через Secure cookies.

Vercel можливий із PostgreSQL pooler і окремим постійним ботом/worker. Внутрішній tick має ліміт 120 секунд; платформа мусить це підтримувати. Короткі serverless таймаути не підходять для закупівель. На VPS немає цього обмеження платформи. Тестовий `.env` із фіктивними ключами в production не використовуйте.

## 3. Ціни

MARKUP_PERCENT=20, SMM_MARKUP_PERCENT=20. Локальна ціна в адмінці — базова, а не фінальна; публічна = база × 1.20. Дані біржі/гаманця не означають його інтеграцію як платіжного провайдера.

FX_MODE=lzt читає `/currency` за LZT_TOKEN. Альтернатива manual: FX_MANUAL_RATES_JSON містить RUB за одиницю RUB/USD/UAH/USDT і FX_MANUAL_UPDATED_AT — UNIX seconds. RUB=1 обов’язково. Ручні значення треба регулярно оновлювати; дані старші 48 годин блокують ціни. USDT не прирівнюється приховано до USD. Новий ручний курс в env потребує перезапуску; кеш курсу — 15 хвилин.

## 4. Платежі WEB

Підключайте лише платіжні методи, схвалені вашим провайдером для вашого бізнесу.

- Crypto Pay: CRYPTO_PAY_TOKEN; спочатку CRYPTO_PAY_TESTNET=true. Webhook POST `https://домен/api/payments/webhook/crypto`. createInvoice: fiat USD, accepted_assets USDT,TON. На баланс зараховується зафіксована сума USDT; TON — засіб сплати invoice, не окремий внутрішній баланс.
- Mono: MONO_TOKEN. Webhook `/api/payments/webhook/mono` передається при створенні invoice. Перевірка X-Sign ключем merchant/pubkey і повторне читання invoice/status; зарахування UAH.
- Stripe: STRIPE_SECRET_KEY + STRIPE_WEBHOOK_SECRET. Endpoint `/api/payments/webhook/stripe`, події checkout.session.completed і checkout.session.async_payment_succeeded. Валюта UAH, readback checkout session; зарахування UAH.

Redirect/натискання «Перевірити» не є доказом оплати. Повідомлення провайдера перевіряються за сирим тілом, а оплата повторно читається сервером. Не застосовуйте middleware, що змінює тіло webhook. UNKNOWN без providerReference: звіряйте invoice у кабінеті провайдера — автоматично новий не створюється. Chargeback/повернення поповнення через платіжний кабінет потребує окремого операторського обліку; поточний код не обробляє їх автоматично.

## 5. Telegram

У BotFather задайте домен Widget, Web App URL і menu button; налаштуйте Mini App short name за потреби. BOT_TOKEN однаковий у сайта й бота. NEXT_PUBLIC_BOT_USERNAME без @. Бот працює окремо, подробиці в його README.

TMA передає повний initData; сервер перевіряє HMAC, давність до 5 хвилин, потім видає HttpOnly сесію на 24 години. Mock не авторизує користувача. WEB legacy Login Widget також перевіряється сервером; email та Telegram створюють окремі облікові записи, якщо раніше не були зв’язані вручну.

Цифрові товари в Telegram оплачуються Stars: задайте STARS_USDT_PER_STAR відповідно до власного тарифу. Наприклад тариф 0.02 означає 0.02 USDT за одну Star, а не офіційний валютний курс. Оплата створює конкретне замовлення; поповнення WEB-балансу через TMA вимкнене. pre_checkout_query перевіряє власника, суму, строк і одноразовість invoice. Повторно скасований користувачем Stars checkout із новим query може бути відхилений: дочекайтеся закінчення резерву (~20 хв), оновіть кошик і створіть нове замовлення. Пізня оплата скасованого замовлення → NEEDS_REVIEW для повернення, без зарахування витратного WEB-балансу.

Один bot polling процес. Його BOT_STATE_DIR має бути на persistent volume. Він записує successful_payment до приватного durable journal і повторює доставку у сайт після збоїв. Втрата диска означає втрату ще не переданих квитанцій; потрібне резервування. Налаштуйте SUPPORT_USERNAME для /paysupport.

## 6. Автоматична видача й worker

SMM_API_URL=https://justanotherpanel.com/api/v2, SMM_CATALOG_MODE=jap. API ключ/баланс постачальника конфігуруються окремо. LZT_TOKEN повинен мати доступ до читання каталогу і дозволеної закупівлі. LZT_BALANCE_ID опціонально задає потрібний баланс.

Після sandbox/контрольної закупівлі увімкніть SMM_LIVE_ORDERS_ENABLED=true та MARKET_LIVE_ORDERS_ENABLED=true. Без цих прапорців покупки відповідних товарів заблоковані до списання. SMM_MAX_ORDER_COST обмежує базову вартість у валюті JAP; MARKET_MAX_ORDER_USDT — роздрібну ціну LZT в USDT. Постачальник може змінити вартість між перевіркою й закупівлею; контрольне приймання обов’язкове.

Бот із COMMERCE_WORKER_ENABLED=true кожні 15 секунд робить POST `/api/internal/commerce/tick` з INTERNAL_API_SECRET. Tick виконує паралельно до одного SMM і одного LZT завдання та звільняє прострочені неоплачені резерви. Для більшої пропускної здатності запускайте окремі worker-и через цей маршрут з lease-захистом; провайдерські rate limits треба врахувати. Окремий планувальник може передавати CRON_SECRET замість INTERNAL_API_SECRET. Тіло `{}`, Authorization: Bearer SECRET. Не вмикайте одночасно старий SMM scheduler без потреби.

UNKNOWN/NEEDS_REVIEW не повторює платну закупівлю. Адміністратор звіряє замовлення у постачальника, потім робить ручну видачу LZT або повернення. SMM PARTIAL/CANCELED потребує перевірки залишку/повернення постачальника; автоматичне часткове грошове повернення не реалізоване. REFUNDING Stars після таймауту потрібно звірити в Telegram — не повторюйте повернення наосліп.

Outbox повідомлень має повторні спроби (до 10), але Telegram sendMessage/sendDocument не гарантує exactly-once: після втрати ACK можливий дублікат повідомлення. Це не дублює замовлення/списання. Email-клієнти без telegramId отримують товари в кабінеті; бот не може повідомити такого клієнта.

## 7. Публікація

Перевірте власні правила, підтримку, всі ціни seed, тексти UK/RU/EN. Увімкніть SEO_ENABLED=true під час build і redeploy: robots/sitemap залежать від build. До цього сайт має noindex. Налаштуйте моніторинг NEEDS_REVIEW/UNKNOWN/REFUNDING, невідправлених повідомлень, балансу постачальника, помилок webhook та резервне відновлення БД. Логи не повинні містити токени, initData, платіжні тіла чи видані логіни/паролі.

Перший приймальний цикл: новий покупець → тестовий депозит → кошик → підтверджена оплата → видача → дубль webhook → перевірка одного списання → повернення. Повторіть окремо для WEB/TMA, JAP, LZT і ручної верифікації на реальній production-like PostgreSQL. У цьому середовищі бойові платежі й деплой не виконувалися.

Офіційні контракти: https://justanotherpanel.com/api · https://docs.lzt.market/ · https://help.cr.bot/en/articles/10279948-crypto-pay-api · https://api.monobank.ua/docs/acquiring.html · https://docs.stripe.com/api/checkout/sessions · https://core.telegram.org/bots/payments-stars

## 10. v8: модулі, сесії, приватна інфраструктура

NEXT_PUBLIC_MINI_APP_NAME — short name із BotFather, без @ і URL. Порожнє значення дає /start-посилання на бота. Застосуйте міграцію `20261006131500_handoff` перед запуском v8. Передана корзина живе 10 хвилин; завершення передачі не є оплатою та не резервує товар.

WEB використовує __Host-legit_user (SameSite=Strict), TMA — __Host-legit_tma (Secure; HttpOnly; SameSite=None; Partitioned). Клієнт надсилає X-Legit-Channel:TMA, сервер перевіряє opaque сесію та її збережений канал. Заголовок сам не авторизує. Адмінська сесія окрема. Старий TMA cookie v7 вимагатиме повторного відкриття Mini App. Потрібно протестувати Android/iOS і Telegram Web із вашим доменом, у тому числі завантаження придбаних файлів.

Приклад VPS: створіть .env у корені, заповніть POSTGRES_PASSWORD, DATABASE_URL=postgresql://legit:URL_ENCODED_PASSWORD@db:5432/legit_assets та справжній домен. POSTGRES_PASSWORD у Compose — звичайний пароль, у DATABASE_URL спеціальні символи URL-кодуються.

```bash
docker compose --env-file .env -f deploy/compose.site.yml build
docker compose --env-file .env -f deploy/compose.site.yml up -d db
docker compose --env-file .env -f deploy/compose.site.yml run --rm site npm run db:deploy
docker compose --env-file .env -f deploy/compose.site.yml run --rm site npm run admin:seed
docker compose --env-file .env -f deploy/compose.site.yml run --rm site npm run admin:create
docker compose --env-file .env -f deploy/compose.site.yml up -d site
```

Скопіюйте nginx.conf.example після заміни домену/сертифікатів; виконайте nginx -t. Docker/nginx приклади не запускалися в QA. PostgreSQL без ports, Next лише 127.0.0.1:3000. Не відкривайте project folder через статичний web root, не публікуйте .env, дампи/бекапи, серверні source maps чи Docker API. Увімкніть резервні копії та перевірте відновлення; обмежте SSH й БД firewall. Не кешуйте HTML із nonce. За наявності CDN він повинен пропускати API без кешу й передавати CSP/cookies незмінно.

HSTS має встановлювати TLS reverse proxy: додайте `add_header Strict-Transport-Security "max-age=15552000" always;` у HTTPS server після перевірки справного HTTPS. Код також встановлює HSTS, коли сам Next бачить HTTPS. Не покладайтеся на HTTP-з’єднання nginx→Next для HSTS.

Старий /api/internal/smm/tick приймає тільки POST з bearer секретом; commerce worker уже використовує POST. Не вставляйте ключі в URL, Git або NEXT_PUBLIC_*.

## 11. v9 worker і діагностика

Оновіть міграції перед новим кодом (`20261006140000_operations`). `compose.site.yml` тепер включає worker; запускайте `up -d site worker`. Коли він активний, у боті COMMERCE_WORKER_ENABLED=false. Бот усе одно обробляє Stars та outbox. Не запускайте зайві worker-и для збільшення частоти без врахування lease і supplier limits.

`npm run worker` — окремий нескінченний Node-процес із послідовними POST tick, таймаутом 110 секунд і паузою 15 секунд; він не друкує секрети. Для supervisor graceful stop налаштуйте stop timeout не менше 120 секунд. Кожен успішний tick оновлює ServiceHeartbeat. Відсутність heartbeat понад 3 хвилини або tick error видно в readiness.

`npm run preflight` після запуску сервісів перевіряє обов’язкові налаштування; strict `npm run launch:check` також вимагає усіх рекомендованих прапорів. Це не перевірка реальної оплати. API readiness доступний лише адміністратору; health публічно повертає лише стан БД. Повна інструкція v9 — START_HERE.md.

# Закрита адмін-панель · v5

Панель доступна на `/admin`, вхід — `/admin/login`. Сайт і бот залишаються окремими деплоями. Адмінські паролі та сесії боту не потрібні.

## Перший запуск на вашому сервері

1. `npm ci`; `.env.example` → `.env`. Заповніть PostgreSQL `DATABASE_URL`, HTTPS `NEXT_PUBLIC_SITE_URL` та FX. Для Vercel використовуйте env у налаштуваннях проєкту; CLI seed/bootstrap запускайте локально чи на захищеному сервері зі з'єднанням до тієї самої БД.
2. Backup наявної БД; `npm run db:generate`, `npm run db:deploy`.
3. `npm run admin:seed`: імпорт бібліотеки логотипів та 13 існуючих послуг. Повторний запуск **не перезаписує змінені ціни, назви та статуси**. Нові логотипи не створюють нових доступних послуг.
4. Встановіть `ADMIN_BOOTSTRAP_EMAIL` і власний унікальний пароль (16–128 символів) через secret store або приватний `.env`. `npm run admin:create`. Команда створює/оновлює ADMIN та відкликає його старі сесії; існуючий користувач із цим email отримує роль ADMIN. Це лише офлайн-команда власника, не публічний endpoint.
5. Видаліть bootstrap пароль із env після створення. Не надсилайте пароль у чат і не додавайте `.env` у git.
6. `VERIFICATION_CATALOG_SOURCE=database`, `npm run build`, `npm start` або деплой Next.js на Vercel. Зайдіть у `/admin/login`.

`archive` — явно обраний режим перегляду v4 без БД, лише для frontend-preview. Зміни через admin API в цьому режимі заборонено. Помилка БД у database mode не підміняється старими JSON-цінами. Без живого PostgreSQL підключити панель до вашого сайту неможливо; credentials/production server у цій сесії не надані.

## Що адміністратор може змінити

Назви UK/RU/EN, базову ціну (2 десяткові знаки) та USD/UAH/USDT, логотип із бібліотеки, групу, публікацію. Базова ціна отримує націнку 20% (MARKUP_PERCENT=20); покупець бачить фінальну суму. Публічний сайт конвертує її у грн + USDT за налаштованим FX. Якщо FX недоступний, суму не вигадуємо.

Нову платформу можна створити з бібліотеки або кнопкою «Додати платформу». За замовчуванням нова послуга прихована. Публікуйте лише після підтвердження, що можете надати супровід власнику акаунта. Видалення історії не передбачено: приховані послуги залишаються в БД, їхня сторінка недоступна відвідувачу.

## Доступ і журнал

- Паролі: salted scrypt; у БД немає відкритого пароля.
- Сесія: випадковий token, у БД лише SHA-256 hash, TTL 12 годин; production cookie `__Host-legit_admin`, HttpOnly, Secure, SameSite=Strict.
- Кожне читання/створення/редагування через admin API перевіряє сесію, термін дії та актуальну роль ADMIN із БД. Клієнт не може призначити роль.
- Кожний POST/PATCH перевіряє Origin на точний configured HTTPS origin. URL має збігатися з доменом, з якого відкриваєте панель; preview domain із іншим Origin не дозволений.
- Вхід: максимум 5 спроб на email / 15 хвилин та 30 загалом / 15 хвилин, buckets у БД. Ліміт рахує й успішні спроби. Помилки credentials однакові для невідомого email, звичайного користувача й неправильного пароля.
- Правки та audit log записуються в одній транзакції. `version` запобігає перезапису застарілого запису: конфлікт ->409, відкрийте послугу після оновлення сторінки.
- Зміна/відкликання ADMIN у БД набирає чинності наступним запитом. Logout видаляє серверну сесію. Bootstrap повторно змінює пароль і відкликає сесії.

Додаткова панель `/admin/operations` керує замовленнями, товарами/складом і категоріями; показує виручку за валютою, кількість клієнтів і проблемні платежі. Ручна видача шифрується та доступна власнику замовлення. Для сторонніх закупівель перед ручною видачею/поверненням потрібно підтвердити звірку з провайдером. Повернення WEB — на баланс; Stars — через Telegram refundStarPayment. При невідомому результаті REFUNDING зверніться до оператора, не повторюйте грошовий запит. MFA не реалізовано.

Вкладка «Товари та склад»: створіть локальний MANUAL або INVENTORY товар, введіть базову ціну. Для складу імпортуйте записи, розділяючи окремі товари рядком `---`; кожний запис шифрується. Один UNIQUE товар списується рівно один раз. Категорії додаються/приховуються; приховування зупиняє новий checkout. Режим видачі вже створеного товару не змінюється. Приховування замість видалення зберігає історію.

Вкладка «Завантажити логотип» приймає PNG до 500 КБ і 4096 × 4096; дані зберігаються в PostgreSQL та віддаються з того самого домену. Далі виберіть цей логотип у редакторі верифікації. Локальні додаткові категорії автоматично з’являються в WEB-навігації. Націнку постачальників адміністратор змінює лише через серверне середовище; довільні покупці не можуть редагувати ціни.

## Логотипи

100 локальних PNG криптобірж та додатковий FACEIT (101 запис BrandAsset), джерела збережено у `src/data/brand-assets.json`. Логотипи належать брендам; додавання в бібліотеку не означає партнерства, гарантії чи наявності послуги. Метадані з CoinGecko: https://www.coingecko.com/en/api . Для відвідувачів зображення завантажуються з вашого домену, без runtime-залежності від CoinGecko API.

# SMM / JustAnotherPanel

Постачальник: https://justanotherpanel.com/api . Реальний API: `POST https://justanotherpanel.com/api/v2`, form-encoded. У цій версії перевірені авторизовані read-only actions `services` та `balance`: отримано 5 755 позицій / 242 категорії, валюта USD. Кількість і тарифи змінюються у постачальника. Реальні закупівлі не виконувалися.

## Каталог

`SMM_CATALOG_MODE=jap` імпортує каталог за стабільними ключами `jap-{serviceId}`; шість статичних відповідностей більше не обмежують вибір. На сервері перевіряються ID, ставка, цілі min/max та формат. На перевіреному snapshot публікується 5 751 послуга, 5 131 з них — Default; чотири позиції мають min вище локального ліміту. Некоректні/нульові тарифи й діапазони не публікуються. Локальний максимум кількості — 10 000 000: якщо постачальник має більший max, сайт звужує його до цього ліміту, не приховує послугу. Назви й категорії зберігаються оригінальними: автоматичне групування за платформою використовується лише для навігації, а не для підтвердження якості/географії/гарантій.

WEB і TMA використовують `/uk/smm`, `/ru/smm`, `/en/smm`. Каталог SSR показує перші 24 позиції, решта завантажуються через `/api/smm/services`. Пошук за назвою, категорією та ID; платформа/категорія; refill; стандартна форма; сортування за retail USDT. Фільтри зберігаються у URL, наприклад `/uk/smm?platform=telegram&supported=1&sort=price-asc`.

Тип `Default` має форму посилання + кількість і серверний розрахунок. `Package`, `Subscriptions`, `Custom Comments`, згадки, polls, traffic зі спеціальними полями та інші типи видимі з позначкою, але не мають розрахунку/замовлення, поки для них не реалізовані спеціальні форми й одиниці тарифу. Їх не можна відправити через стандартний enqueue: supplierService відхиляє такий тип на сервері. Ставка за 1000 використовується лише для `Default`.

Посилання перевіряються як HTTPS URL без credentials/port. Для відомих платформ діє allowlist доменів; для інших — публічний домен без IP/локальних суфіксів. Query зберігається (YouTube `?v=`); це не перевірка існування/публічності профілю і не заміна специфічних вимог у назві послуги. Сервер сайту не завантажує URL клієнта. Перед запуском продажів перевірте вимоги та якість обраних пакетів у панелі.

## Налаштування сервера

```dotenv
SMM_API_URL="https://justanotherpanel.com/api/v2"
SMM_CATALOG_MODE="jap"
SMM_API_KEY="" # тільки секрет на сервері сайту
SMM_MARKUP_PERCENT="20"
SMM_MAX_ORDER_COST="100" # у валюті supplier balance, зараз USD
SMM_LIVE_ORDERS_ENABLED="false"
```

Ключ не включений в архів і не передається в браузер/бот. На хостингу вставте його в server environment. Для грн/USDT потрібен справжній FX: `FX_MODE=lzt` + `LZT_TOKEN`, або явно налаштований manual snapshot із RUB per currency unit та свіжим UNIX timestamp. Без валідного FX каталог відображається без ціни, розрахунок відхиляється. Немає вигаданого курсу за замовчуванням. Націнка 20% змінюється через `SMM_MARKUP_PERCENT`; дробові суми рахуються Decimal, до копійки округлюються вгору після розрахунку всього замовлення.

Каталог/валюта кешуються у пам’яті процесу на 5 хвилин; відсутність API не підміняється архівом. Для іншої сумісної панелі встановіть `SMM_CATALOG_MODE=mapped` і `SMM_APPROVED_SERVICE_MAP_JSON` із шістьма попередніми ключами (`tg-subs`, `tg-react`, `ig-followers`, `ig-likes`, `tt-subs`, `tt-likes`). Це окремий ручний режим.

Після міграцій PostgreSQL виконайте `npm run smm:sync`. Команда зчитує актуальні ставки й записує лише підтримувані Default-послуги як `Product` з slug `smm-jap-{id}`, supplier ID, min/max, назвою та категорією. Вона атомарно вимикає старі `smm-v2` товари, що зникли. Спочатку отримує API+FX; у разі помилки нічого не видаляє. Команда не купує послуги. Імпорт великого каталогу може тривати кілька хвилин. `Product.price` — лише оцінка за одиницю (6 знаків), checkout має рахувати повну кількість заново. Повторюйте sync scheduler-ом відповідно до вашої інфраструктури. SMM цінами керує серверний тариф постачальника та глобальна націнка env; вручну їх у панелі не підміняємо.

## Оплата і бот v7

Конфігуратор додає Default-послугу до кошика з supplier ID, кількістю та нормалізованим посиланням. Checkout повторно читає ставку на сервері, перевіряє очікувану фінальну суму і баланс. WEB оплачує через свій баланс, TMA через Stars. Платіж створює Order/OrderItem та SmmJob атомарно. Для email-покупців Telegram ID не потрібний; результат видно в кабінеті.

Бот працює окремим процесом: COMMERCE_WORKER_ENABLED=true робить POST `/api/internal/commerce/tick` з INTERNAL_API_SECRET. Той самий маршрут може викликати окремий scheduler із CRON_SECRET. Кошти не списуються, доки SMM_LIVE_ORDERS_ENABLED=false. Після контрольного sandbox/малого замовлення в погодженому середовищі увімкніть прапорець і переконайтеся, що worker працює. Бот не отримує JAP key.

Старі `/api/internal/smm/enqueue`, `/jobs/:id`, `/tick` залишені для сумісності; новий checkout уже ставить завдання автоматично, повторно enqueue викликати не потрібно. OrderItem.lineTotal — точна фінальна сума позиції; unitPrice може мати округлення при великій кількості. Статуси й залишок видно покупцю; завершення надсилається прив’язаному Telegram-користувачу через outbox.

## Надійність і межі

Worker використовує leases і CAS; тільки один worker відправляє конкретну задачу. До `add` повторюються безпечні read/preflight помилки. Після відправлення `add` таймаут, некоректна відповідь, прострочений SENDING або збій DB commit означають UNKNOWN/NEEDS_REVIEW; автоматичного повторного add немає. API не дає стандартного idempotency key. Потрібна ручна звірка в JAP; `/admin/operations` показує provider order ID/помилку й дозволяє повернення після перевірки.

`Completed` без залишку завершує позицію/замовлення, partial/canceled/unknown вимагають перевірки. Повне повернення замовлення адміністратором реалізоване після звірки; часткове автоматичне повернення та refill/cancel API actions не реалізовані. API `add` не має атомарного price cap, тому preflight не гарантує ціну в момент закупівлі. Availability refill/cancel береться з boolean API; текст у назві може відрізнятися і не перетворюється на гарантію.

## Перевірка

Див. QA_V7.md. Поточні інтеграційні тести проходять оплачений checkout → один add → polling Completed та перевіряють блокування checkout, коли закупівлі вимкнені. Використано ізольовану БД і API fixtures; реальних замовлень JAP не створено.
